# Repository Guidelines

## Project Structure & Module Organization

`frontend/` contains the Angular 22 standalone application. Put shared UI in `frontend/src/app/shared/`, session logic in `core/`, and domain pages, routes, models, styles, and services in `features/` (`management`, `operations`, `communications`, `cleaning`, `reports`, and `portal`). Global styles live in `frontend/src/styles.scss`; public assets, including the official IF Goiano mark, live in `frontend/public/`. Keep unit tests beside their source as `*.spec.ts`; browser tests live in `frontend/e2e/`. `backend/` contains the Spring Boot application, feature packages under `src/main/java/br/edu/ifgoiano/sager/`, Flyway migrations under `src/main/resources/db/migration/`, and tests under `src/test/java/`. `openspec/specs` is the source of behavior; `docs/ARQUITETURA.md` records architecture, decisions and institutional pending items; `docs/MANUAL.md` is the user guide by profile; `docs/DESENVOLVIMENTO.md` describes the method, code standards, tests and how to make a change; `PRODUCT.md`, `DESIGN.md`, and `.impeccable/config.json` hold the approved visual direction. `LICENSE` is the restricted-use license: all rights reserved, with a use license for IF Goiano. Do not replace it with an open-source license unless the owners decide so or an IF Goiano rule or contract on ownership requires it (LICENSE item 6).

## Build, Test, and Development Commands

Run these from `frontend/`:

- `npm ci` — install the locked dependencies.
- `npm start` — serve the application at `http://localhost:4200/acesso`, proxying `/api` to the backend at `127.0.0.1:8080`.
- `npm run build` — compile the production bundle and check Angular templates.
- `npm test -- --watch=false` — run unit and component tests once.
- `npm run test:e2e` — run Playwright journeys; its configuration starts the dev server.

Run `./mvnw -B -ntp verify` from `backend/` (`.\mvnw.cmd` on Windows) with JDK 21 and Docker available. Testcontainers creates disposable PostgreSQL databases; no application database or account is required for tests. Run `./sager ci` from the root before merging or deploying: it runs the backend, frontend, infrastructure and OpenSpec checks on this machine, with logs in `.ci/`. The GitHub Actions workflow is disabled. See `backend/README.md` for local provisioning and `docs/OPERACAO.md` for the Docker environment, the local checks and browser test selection.

## Coding Style & Naming Conventions

Use two-space indentation, single quotes, and a 100-character print width as configured in `frontend/.prettierrc`. Format touched files with `npx prettier --write <path>`. Follow existing kebab-case filenames and suffixes such as `resident-form.component.ts`, `courses.page.ts`, and `resident-api.service.ts`. Prefer standalone components, typed Reactive Forms, Signals, and feature-level services. Keep important actions clearly labeled and preserve the approved responsive design; use Impeccable for UI changes.

## Testing Guidelines

Angular unit tests use Vitest through `ng test`; end-to-end tests use Playwright and `@axe-core/playwright`. Add or update focused `*.spec.ts` tests for changed rules, permissions, forms, and navigation. Cover critical paths and accessibility behavior in `frontend/e2e/`. Backend integration tests use JUnit and PostgreSQL Testcontainers; verify migrations, constraints, permissions, CSRF, version conflicts and concurrent changes for the affected feature. Browser journeys with intercepted API calls verify the interface; they do not prove the complete application works against PostgreSQL. No numeric coverage threshold is configured; report the commands run and any untested risk.

## Commit & Pull Request Guidelines

History uses small, purpose-based commits such as `feat(frontend): ...`, `test(e2e): ...`, `docs: ...`, and `chore(repo): ...`. Keep unrelated changes in separate commits. In pull requests, summarize the behavior, cite the OpenSpec change and the requirements it touches, list verification commands, and include before/after screenshots for visual changes.

## Security & Demo Data

Use synthetic records only. The demonstration mode (RF027) uses profile selection and in-memory synthetic data from the `*-demo` services, never calls the API, and is unavailable in production, where the gateway marks the build as production and returns 404 for `/demonstracao`. Do not substitute demo data after an API failure. The project has chosen SAGER-owned enrollment/password accounts; Google and SUAP integrations are deferred. Profiles `local` and `production` use gestor accounts that the operator creates with the account CLI (`create` accepts only `gestor`), plus accounts created atomically with a resident or supervisor record, JDBC sessions, CSRF and record authorization. Local binds loopback; production requires separate migration/runtime roles, external secrets and the HTTPS proxy in infra/production/. Keep APIs closed for unknown profiles. Reject invalid production/migration configurations or combined production/migration profiles before database initialization. Technical evidence never replaces institutional acceptance, and external providers remain distinct. Do not commit credentials, resident data, the excluded DOCX/PDF/ZIP originals, or generated build output. Keep the official IF Goiano mark unmodified.

## Current Domain Decisions

In the integrated management resources, gestor and supervisor have equal read/write permissions, including moves, except supervisor records: by the owner's decision of 2026-10-31, solely the gestor lists, reads, creates and edits them, and creating one requires a password that atomically creates the linked login account. New resident POST/PUT requests require name, enrollment, birth date, courseId and entry year (`entryYear`), which the form suggests from the first 4 digits of the enrollment; format rules apply only to new or changed values, so legacy data stays readable and editable. Flyway V10 preserves legacy residents without birth dates for reading while requiring the date on future inserts and updates. The backend stores resident names with every word capitalized; Flyway V22 applies this to existing residents and their linked accounts, leaving guardians and historical snapshots as recorded because signature checks compare guardian names exactly. Resident enrollment is entered manually until an authorized SUAP integration exists, and assisted resident creation atomically creates a linked login account with the chosen password. Institutional email is optional for residents and must end in @estudante.ifgoiano.edu.br when filled; requests select courseId. A new course, or one whose name, level or duration changes, requires a level (`MEDIO` or `SUPERIOR`) and a duration (`durationYears`) of 1 to 6 years; legacy courses without them stay readable and can still be activated or deactivated. The server computes each resident's stage, expected exit and `concluded` flag from the entry year, the 5th enrollment character, the course duration and the extension, with America/Sao_Paulo dates; it refuses to place or transfer a concluded resident with 409 `resident_concluded`, and a daily job closes the active room allocation of concluded residents with reason `CONCLUSION` and `SYSTEM_JOB` audit. An accommodation has an optional age group (`MENORES` or `MAIORES`, under or over 18 in America/Sao_Paulo) that its rooms inherit; placing or transferring a resident into another group, or one without a birth date into an accommodation with a group, is refused with 409 `age_group_mismatch` or `birth_date_required`, active allocations never change by themselves, and the night call keeps an adults accommodation while it still has an allocated minor. All roles log in with enrollment; staff recovery is administrative and eligible residents recover by registered name, birth date and active guardian name when present. Long exits require one guardian authorization confirmed by a supervisor against the current document revision before a separate human approval. Audit records have permanent retention.

Operations are supervisor-only except the minor resident's own linked exit requests; the server refuses exit requests from residents who are 18 or older in America/Sao_Paulo or have no birth date. Gestor does not inherit these permissions. Night calls freeze allocated minors at opening; justified absence requires authorization and physical departure valid at opening, and the system records it at opening when exactly one exit qualifies, which the supervisor can correct. Short and long exits use the server clock and America/Sao_Paulo civil dates; only a supervisor records physical movement. Long exits require a guardian authorization file received by WhatsApp or attached manually, confirmed by a supervisor who declares having checked guardian, document and revision on the current revision, with intact private files, before a separate human approval. This is a recorded human review, not an electronic signature under Lei 14.063/2020; screens and documents must say "autorização conferida" and never claim a signature or legal validity. Webhook events and message delivery, reading or receipt never confirm an authorization or grant approval, and manual attachment stays available when WhatsApp is down. There is no external signature provider. Keep the self-hosted WhatsApp gateway disabled until explicitly configured; the dedicated number, operation (docs/whatsapp/OPERACAO.md) and institutional acceptance of this unofficial integration are external. WhatsApp conversations, including media, session and QR routes, are supervisor-only: gestor and resident roles do not inherit them, the gateway stays off the backend network, conversation messages never authorize an exit, audit records for them carry metadata only, and their retention awaits an institutional decision. Preserve history and transactional audit for corrections and system expiration. Discipline (occurrences, internal notifications, warnings and commitment terms) and institutional notices are managed only by the supervisor; gestor has no access, and residents only read their own warnings, terms and notices and record acknowledgment. Only the supervisor records and corrects cleaning evaluations; gestor and supervisor read them, and residents read only their own. All three roles read the ranking; residents see scores only for their own rooms. Reports (query and export) and the audit query (API only) are for gestor and supervisor. Behavior rules live in openspec/specs/<capability>; local choices that still await institutional approval are listed in docs/ARQUITETURA.md.

## OpenSpec workflow

Every behavior change starts as an OpenSpec change in `openspec/changes/<name>/`. The OpenSpec skills live in `.agents/skills/` and `.claude/skills/`, and `openspec/config.yaml` sets the language and the artifact rules.

1. Propose: write `proposal.md` (why, what changes, impact and what is out of scope), delta specs in `specs/<capability>/spec.md`, `design.md` (each decision with its rejected alternative, plus what the institution or the operator must still decide) and `tasks.md` (each task names how it is verified). Cite the spec requirement or AGENTS.md rule the change affects.
2. Apply: implement the tasks in order and mark a task `- [x]` only after its verification passes.
3. Validate: `openspec validate <name> --strict` must pass.
4. Verify: confirm the implementation matches the proposal, specs and design.
5. Archive: `openspec archive <name>` merges the delta specs into `openspec/specs`.

A change that only touches documentation or tooling declares `skip_specs: true` in its `.openspec.yaml` and has no delta spec. Archived changes in `openspec/changes/archive/` are history and are never edited. `./sager ci` runs `npx @fission-ai/openspec@2.0.0 validate --all --strict`, so every spec and every active change must stay valid.
