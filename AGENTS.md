# Repository Guidelines

## Project Structure & Module Organization

`frontend/` contains the Angular 22 standalone application. Put shared UI in `frontend/src/app/shared/`, session logic in `core/`, and domain pages, routes, models, styles, and services in `features/` (`management`, `operations`, `communications`, `reports`, and `portal`). Global styles live in `frontend/src/styles.scss`; public assets, including the official IF Goiano mark, live in `frontend/public/`. Keep unit tests beside their source as `*.spec.ts`; browser tests live in `frontend/e2e/`. `backend/` contains the Spring Boot application, feature packages under `src/main/java/br/edu/ifgoiano/sager/`, Flyway migrations under `src/main/resources/db/migration/`, and tests under `src/test/java/`. The root PRD, technical specification, `PRODUCT.md`, `DESIGN.md`, and `.impeccable/` record requirements and approved visual direction.

## Build, Test, and Development Commands

Run these from `frontend/`:

- `npm ci` — install the locked dependencies.
- `npm start` — serve the demo at `http://localhost:4200/acesso`.
- `npm run build` — compile the production bundle and check Angular templates.
- `npm test -- --watch=false` — run unit and component tests once.
- `npm run test:e2e` — run Playwright journeys; its configuration starts the dev server.

Run `./mvnw -B -ntp verify` from `backend/` (`.\mvnw.cmd` on Windows) with JDK 21 and Docker available. Testcontainers creates disposable PostgreSQL databases; no application database or account is required for tests. See `backend/README.md` for local provisioning and `docs/CI.md` for the GitHub Actions pipeline and browser test selection.

## Coding Style & Naming Conventions

Use two-space indentation, single quotes, and a 100-character print width as configured in `frontend/.prettierrc`. Format touched files with `npx prettier --write <path>`. Follow existing kebab-case filenames and suffixes such as `resident-form.component.ts`, `reports.pages.ts`, and `management-demo.service.ts`. Prefer standalone components, typed Reactive Forms, Signals, and feature-level services. Keep important actions clearly labeled and preserve the approved responsive design; use Impeccable for UI changes.

## Testing Guidelines

Angular unit tests use Vitest through `ng test`; end-to-end tests use Playwright and `@axe-core/playwright`. Add or update focused `*.spec.ts` tests for changed rules, permissions, forms, and navigation. Cover critical paths and accessibility behavior in `frontend/e2e/`. Backend integration tests use JUnit and PostgreSQL Testcontainers; verify migrations, constraints, permissions, CSRF, version conflicts and concurrent changes for the affected feature. Browser journeys with intercepted API calls verify the interface; they do not prove the complete application works against PostgreSQL. No numeric coverage threshold is configured; report the commands run and any untested risk.

## Commit & Pull Request Guidelines

History uses small, purpose-based commits such as `feat(frontend): ...`, `test(e2e): ...`, `docs: ...`, and `chore(repo): ...`. Keep unrelated changes in separate commits. In pull requests, summarize the behavior, cite relevant PRD requirements or acceptance criteria, list verification commands, and include before/after screenshots for visual changes.

## Security & Demo Data

Use synthetic records only. The public demonstration uses profile selection and in-memory data. The project has chosen SAGER-owned enrollment/password accounts; Google and SUAP integrations are deferred. Profiles `local` and `production` use operator-provisioned accounts, plus accounts created atomically with a resident or supervisor record, JDBC sessions, CSRF and record authorization. Local binds loopback; production requires separate migration/runtime roles, external secrets and the HTTPS proxy in infra/production/. Keep APIs closed for unknown profiles. Reject invalid production/migration configurations or combined production/migration profiles before database initialization. Production disables demonstration access. Technical evidence is in docs/fase-7/QA.md; institutional acceptance and external providers remain distinct. Do not substitute demo data after a local API failure. Do not commit credentials, resident data, the excluded DOCX/PDF/ZIP originals, or generated build output. Keep the official IF Goiano mark unmodified.

## Current Domain Decisions

In the integrated management resources, gestor and supervisor have equal read/write permissions, including moves, except supervisor records: by the owner's decision of 2026-10-31, which replaces D01 on this point only, solely the gestor lists, reads, creates and edits them, and creating one requires a password that atomically creates the linked login account. New resident POST/PUT requests require name, enrollment, birth date and courseId; format rules apply only to new or changed values, so legacy data stays readable and editable. Flyway V10 preserves legacy residents without birth dates for reading while requiring the date on future inserts and updates. The backend stores resident names with every word capitalized; Flyway V22 applies this to existing residents and their linked accounts, leaving guardians and historical snapshots as recorded because signature checks compare guardian names exactly. Resident enrollment is entered manually until an authorized SUAP integration exists, and assisted resident creation atomically creates a linked login account with the chosen password. Institutional email is optional for residents and must end in @estudante.ifgoiano.edu.br when filled; requests select courseId. All roles log in with enrollment; staff recovery is administrative and eligible residents recover by registered name, birth date and active guardian name when present. Long exits require one guardian authorization confirmed by a supervisor against the current document revision before a separate human approval. Audit records have permanent retention. Health content is a separate resource: an active professional grant and care assignment are required, with explicit compatible sharing or custody. Management authority does not grant access to health notes. The health role has no management CRUD; the resident's own health route derives its identity from the server account link. Health revisions are immutable and are not automatically deleted. Health content audit events are excluded from the global audit query before pagination.

Operations are supervisor-only except the resident's own linked exit requests. Gestor does not inherit these permissions. Night calls freeze allocated minors at opening; justified absence requires authorization and physical departure valid at opening, and the system records it at opening when exactly one exit qualifies, which the supervisor can correct. Short and long exits use the server clock and America/Sao_Paulo civil dates; only a supervisor records physical movement. Long exits require a guardian authorization file received by WhatsApp or attached manually, confirmed by a supervisor who declares having checked guardian, document and revision on the current revision, with intact private files, before a separate human approval. This is a recorded human review, not an electronic signature under Lei 14.063/2020; screens and documents must say "autorização conferida" and never claim a signature or legal validity. Webhook events and message delivery, reading or receipt never confirm an authorization or grant approval, and manual attachment stays available when WhatsApp is down. There is no external signature provider. Keep the self-hosted WhatsApp gateway disabled until explicitly configured; the dedicated number, operation (docs/whatsapp/OPERACAO.md) and institutional acceptance of this unofficial integration are external. WhatsApp conversations, including media, session and QR routes, are supervisor-only: gestor, resident and health roles do not inherit them, the gateway stays off the backend network, conversation messages never authorize an exit or grant health access, audit records for them carry metadata only, and their retention awaits an institutional decision. Preserve history and transactional audit for corrections and system expiration. Local technical policies are in docs/fase-3/README.md and docs/fase-4/CONTRATO.md; they are delegated implementation choices, not institutional approval.
